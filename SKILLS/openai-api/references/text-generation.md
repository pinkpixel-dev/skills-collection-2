# Text Generation

## Core call shape

Use the Responses API (`client.responses.create`) for direct model requests. The model's output lives in `response.output`, an array of typed Items. For simple text-only cases, `response.output_text` aggregates all text output into one string — but don't assume that's the *only* thing in `output`; tool calls, reasoning items, etc. can also appear there.

## Prompt engineering basics

Prompt engineering = writing instructions that reliably produce the output you want. Because generation is non-deterministic, treat it as iterative: pin production apps to a specific model **snapshot** (e.g. `gpt-5.5-2026-04-23`, not just `gpt-5.5`) so behavior doesn't shift under you, and build a small eval/test suite for your prompts so you can detect regressions when you change prompts or upgrade models.

## Choosing a model/API

- **Reasoning models** (e.g. `gpt-5.6`, o-series) behave differently from standard chat models and get measurably better results on the **Responses API** than Chat Completions — recommend Responses whenever a reasoning model is in play.
- Default recommendation for any new text-generation app: Responses API over Chat Completions, full stop.

## Message roles & instruction priority

Two ways to give the model guidance, which are roughly equivalent:

**A) Top-level `instructions` + `input`:**
```typescript
const response = await client.responses.create({
  model: "gpt-5.6",
  reasoning: { effort: "low" },
  instructions: "<system-level guidance: tone, goals, examples>",
  input: "<the user's actual message>",
});
```

**B) Explicit role-tagged messages in `input`:**
```typescript
const response = await client.responses.create({
  model: "gpt-5.6",
  reasoning: { effort: "low" },
  input: [
    { role: "developer", content: "<system-level guidance>" },
    { role: "user", content: "<the user's message>" },
  ],
});
```

Priority order (from the OpenAI model spec's chain of command):

| Role | Priority |
|---|---|
| `developer` | Instructions from the app developer — highest priority, takes precedence over `user` |
| `user` | Instructions from the end user — lower priority than `developer` |
| `assistant` | Messages generated by the model itself |

Think of `developer` messages like a function definition (the rules) and `user` messages like the arguments passed to it.

**Important**: `instructions` only applies to the *current* request. If you're chaining turns with `previous_response_id`, the `instructions` from earlier turns are NOT carried forward automatically — resend them each time if you need consistent system behavior across a conversation.

## Versioning prompts in code (not via the API's saved-prompt objects)

OpenAI is deprecating reusable prompt *objects* stored via the API (`v1/prompts`): prompt creation is being de-emphasized starting mid-2026, with `v1/prompts` scheduled to shut down. **Recommendation for new work: keep prompts in your own codebase, not as API-managed objects.**

Practical pattern:
- Keep a small prompt-builder module near the feature it supports (e.g. `prompts/summarize.ts`).
- Use typed function args or schemas for the dynamic parts (customer data, files, task options) rather than string-templating blindly.
- Build `instructions` and `input` in code, then pass straight to `responses.create`.
- Write fixtures/tests/evals before changing a production prompt.
- Roll out prompt changes through your normal deploy process (feature flags, staged config) rather than editing a live prompt object.

If existing code calls a saved prompt by ID/version, that needs to be migrated into code-based prompt construction — flag this to the user if you see prompt IDs floating around in their codebase.
